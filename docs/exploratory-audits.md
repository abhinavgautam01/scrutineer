# Exploratory Audits

Triage normally requests a threat model, whose completion queues planned `security-deep-dive` scans. To check for blind spots in that plan, Scrutineer additionally selects one third of eligible triage invocations for one independent random-dig audit. Selection is a stable hash of the triage scan ID, so restarting the server or replaying a completion callback does not roll the probability again.

An extra audit is eligible only after a successful, full-mode threat-model scan requested by triage has at least one queued, running, or completed planned deep dive in the same scope and group. Manual threat-model runs, failed threat models, diff rescans, and repositories with no planned audits do not schedule extras. The extra uses the active deep-dive skill's model preference and normal turn cap. It shares the planned batch's finding-deduplication group. Automatic redelivery never schedules a second extra, including after failure or cancellation; an operator may explicitly retry the recorded scan.

The worker chooses uniformly among distinct directories containing recognized source-file extensions in the filtered checkout. Root-level source is represented by `.`. Selection ignores `.git`, symlink files and directories, documentation-only directories, and paths outside the requested subproject. The existing skill path filters and repository `scan_config.skip` exclusions run first and remain authoritative. A repository without an eligible source directory produces a visible scan error before an agent is invoked. The source-extension list is conservative; extensionless scripts and unlisted languages are not sampling candidates.

The scan receives a minimal independent question and the same findings schema, not the planned-audit instructions. It receives neither the staged threat model nor `scan_config`, recon, or prior scan reports. Its callback token permits only schema validation of its own report; reads and enqueues are blocked. This is context isolation, not a separate network sandbox: the configured runner's normal egress controls still apply. The selected directory, exploration mode, triage lineage, and actual prompt are recorded for inspection. Retries keep the target directory; if it is no longer eligible, the retry fails visibly rather than silently choosing another target.

Reports must name their limited scope. The ordinary findings parser, fingerprint deduplication, High/Critical revalidation, and subsequent review gates remain unchanged. An exploratory scan is never accepted as the baseline for a later diff scan. This implements the random-dig option in issue #727; it does not also enqueue an adversarial sweep or override explicit operator exclusions.
